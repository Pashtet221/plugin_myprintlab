# Print Proof Workflow 1.5.0

## Проверка цветности при расчёте цены

1. Откройте страницу товара в приватном окне браузера, затем DevTools → **Network** и включите **Preserve log**.
2. По очереди выберите `4+0` и `4+4`. Для каждого выбора откройте запрос расчёта цены и проверьте во вкладке **Payload**, что `ppw_color` равен выбранному значению.
3. В том же payload раскройте JSON поля `ppw_config`: у параметра цветности поле `value` должно совпадать с `ppw_color`.
4. Добавьте оба варианта в корзину отдельными позициями и оформите тестовый заказ. В webhook `print_order_created` проверьте `items[].config.params`: значение цветности каждой позиции должно совпадать с выбором.

Проверять нужно именно новый запрос после переключения опции, а не старую запись в Network. После обновления плагина файл `assets/ppw.js` получает новую версию в URL, однако приватное окно или очистка кеша CDN/оптимизатора исключат загрузку старого JavaScript. Поле `ppw_color` относится к запросу расчёта цены на странице товара, а заказ плагин отправляет отдельным webhook в формате `items[].config`.

## Поля позиции заказа

У каждой строки заказа с загруженным файлом в `line_items[].meta_data` создаются публичные поля:

- `isPDFCheked` — `False`, пока файл ожидает проверки, и `True`, когда типография установила результат проверки (написание `Cheked` сохранено как часть контракта интеграции);
- `pdfCheckResult` — детальный статус файла.

Возможные значения `pdfCheckResult`:

- `pending` — файл ожидает проверки (`isPDFCheked: False`);
- `accepted` — типография приняла файл (`done`), подтверждение клиента не требуется;
- `failed` — файл не принят, клиент должен загрузить замену;
- `awaiting_modified_confirmation` — типография изменила файл под формат и требования, клиент должен скачать и утвердить результат;
- `awaiting_print_confirmation` — типография проверила и подготовила файл к печати, клиент должен скачать и утвердить результат;
- `approved` — клиент утвердил файл.

Поля создаются вместе с позицией, поэтому доступны в WooCommerce REST API. В исходящем webhook эти же значения передаются как `isPDFCheked` (JSON boolean) и `pdfCheckResult`.

## Доступные клиенту действия

На странице деталей заказа возле каждой позиции показываются текущий статус и комментарий типографии.

- При `failed` клиент может загрузить новый файл или удалить позицию. При загрузке статус только этой позиции вернётся в `pending`, старый подготовленный файл перестанет показываться, а полный заказ повторно отправится через webhook `print_order_created`.
- При `awaiting_modified_confirmation` или `awaiting_print_confirmation` клиент может скачать подготовленный файл и нажать «Утверждаю» либо удалить позицию. После утверждения статус позиции изменится на `approved`. Эти два состояния сохраняются раздельно: исправление неподходящего макета и техническая подготовка принятого макета.

Оплата закрыта, пока **каждая** оставшаяся позиция с файлом не получит статус `accepted` или `approved`. После принятия/утверждения всех оставшихся файлов заказ автоматически переходит в `awaiting-payment` («Ожидает оплаты»), а клиент видит ссылку WooCommerce на оплату на странице заказа и получает её по email.

## Исходящий webhook при создании заказа

В массиве `items` передаются `item_id`, `isPDFCheked`, `pdfCheckResult`, исходный файл и параметры печати. `item_id` нужен для ответа по конкретному файлу.

Webhook из настроек **WooCommerce → Print Workflow** поддерживает как классическое оформление заказа, так и Checkout Blocks/Store API. Успешной считается только доставка с HTTP-кодом 2xx; при ошибке выполняется до четырёх повторных попыток, а подробности записываются в журнал WooCommerce с источником `ppw-webhook`. Это отдельный webhook плагина; стандартные вебзацепы WooCommerce продолжают работать независимо.

## Callback типографии

Endpoint:

`POST /wp-json/ppw/v1/file-result`

Заголовок:

`X-PPW-Secret: <секрет из WooCommerce → Print Workflow>`

### 1. Файл полностью не принят

```json
{
  "order_id": 123,
  "item_id": 456,
  "result": "failed",
  "message": "Недостаточное разрешение. Загрузите новый файл."
}
```

### 2. Файл изменён под требования

```json
{
  "order_id": 123,
  "item_id": 456,
  "result": "modified",
  "proof_url": "https://example.com/files/fixed.pdf",
  "message": "Размер приведён к формату. Проверьте макет."
}
```

### 3. Файл проверен и подготовлен к печати

```json
{
  "order_id": 123,
  "item_id": 456,
  "result": "print_ready",
  "proof_url": "https://example.com/files/print-ready.pdf",
  "message": "Файл подготовлен к печати. Проверьте и утвердите его."
}
```

Для обоих результатов, требующих утверждения, обязателен `proof_url` либо загрузка `proof_file` в multipart-запросе. Старые значения callback `passed`/`success` поддерживаются как синонимы `print_ready`, а `changed` — как синоним `modified`.

## Ручное управление

В админке заказа для каждой загруженной позиции можно выбрать результат проверки, указать комментарий клиенту и URL подготовленного файла. После сохранения плагин обновляет публичные meta-поля и пересчитывает общий статус заказа.


## Контракт интеграции с типографией (коды Дениса)

Все результаты передаются в существующий `POST /wp-json/ppw/v1/file-result` с `X-PPW-Secret`. При выключенных красивых ссылках используйте `POST /?rest_route=/ppw/v1/file-result`. Поля: `order_id`, `item_id`, `result`, необязательное `message`, а для подготовленного файла — `proof_url` или multipart `proof_file`.

| Код типографии в `result` | Статус `pdfCheckResult` | Действие клиента |
| --- | --- | --- |
| `done` | `accepted` | Не требуется |
| `ChangedNeedApprov` | `awaiting_modified_confirmation` | Скачать исправленный макет и утвердить либо удалить позицию |
| `NeedApprov` | `awaiting_print_confirmation` | Скачать подготовленный к печати макет и утвердить либо удалить позицию |
| `needNewFile` | `failed` | Загрузить новый файл либо удалить позицию |

Регистр кодов не важен. Старые коды `failed`, `rejected`, `modified`, `changed`, `print_ready`, `passed`, `success` остаются допустимыми. `done` означает именно принятие без дополнительного подтверждения.

Для заказа 37373 пример callback (номера позиций берите из `items[].item_id` webhook, не подставляйте внутренние номера файлов типографии):

```json
{
  "order_id": 37373,
  "item_id": 456,
  "result": "ChangedNeedApprov",
  "message": "Файл обрезан под требования. Проверьте результат.",
  "proof_url": "https://example.com/files/fixed.pdf",
  "revision": 0
}
```

Для загрузки файла вместо ссылки отправьте `multipart/form-data` с текстовыми полями `order_id`, `item_id`, `result`, `message`, `revision` и файлом `proof_file`. Разрешены PDF, AI, PSD, PNG и JPG/JPEG с проверкой средствами WordPress. Загруженный файл сохраняется в uploads, а его URL показывается клиенту для скачивания. Ссылку `proof_url` плагин сохраняет, без скачивания удалённого файла; она должна быть доступна клиенту.

Заголовок `X-PPW-Secret` должен совпадать с секретом в **WooCommerce → Print Workflow**. Не передавайте секрет в URL. Без правильного секрета сервер возвращает 403; без подготовленного файла для двух статусов ожидания — 400; для отсутствующего заказа/позиции — 404. Изменение оплаченного/закрытого заказа или уже утверждённого клиентом файла — 409.

## Повторная отправка полного заказа

После загрузки замены, утверждения или удаления позиции плагин пересчитывает итог и отправляет на **тот же URL** webhook **тот же `event: print_order_created`** с актуальными `items`, `file_urls`, `total`, `status`. Удалённая позиция отсутствует в `items`. Подготовленный файл передаётся как `items[].proof_url`; исходник остаётся в `items[].file_url`.

Дополнительные поля:

- `action`: `checkout` при создании; далее `replace_file`, `confirm_item_proof` или `remove_item`;
- `changed_item_id`: изменённая или удалённая позиция (`0` при создании);
- `revision`: `0` при создании, затем увеличивается после каждого действия клиента;
- `event_id`: стабильный идентификатор вида `ppw-order-37373-revision-2`, одинаковый при повторной доставке одного изменения.

На стороне типографии webhook нужно обрабатывать как обновление существующего заказа по `order_id`, а не создавать новый заказ при каждой доставке. Для повторной проверки выбирайте позиции с `pdfCheckResult: pending`; после замены именно эта позиция сбрасывается в `pending`. Уже принятые и утверждённые файлы повторно переводить в ожидание подтверждения не нужно. `confirm_item_proof` сообщает об утверждении, `remove_item` — об актуальном составе заказа.

Возвращайте HTTP 2xx после принятия webhook. При сетевой ошибке или другом HTTP-коде плагин делает до четырёх повторных попыток через WP-Cron, журнал — источник `ppw-webhook`. Повторные `event_id` должны обрабатываться идемпотентно. При получении более новой `revision` используйте новый полный состав заказа; старые отложенные отправки плагин игнорирует. На рабочем сайте WP-Cron должен регулярно выполняться.

В callback рекомендуется возвращать полученную `revision`. Ответ на устаревшую ревизию отклоняется с 409: используйте последнюю полученную ревизию и актуальный состав заказа. Поле пока необязательно для совместимости, но без него нельзя отличить запоздалый результат старой проверки от результата проверки нового файла.

Удаление пересчитывает сумму оставшихся позиций, скидки купонов и налоги через WooCommerce. Существующие отдельные сборы и стоимость доставки сохраняются; если удалена последняя товарная позиция, они тоже удаляются, итог становится нулевым и заказ отменяется. Действия доступны только для неоплаченного заказа и проверяются по владельцу/ключу заказа и nonce. Файлы на диске автоматически не удаляются вместе с позицией.

## Локальная проверка

Используйте отдельный тестовый WordPress с активными WooCommerce и плагином и работающим HTTP-сервером по адресу `home` этого сайта. Не запускайте интеграционные проверки на рабочем магазине: они создают тестовые заказы и купон, временно меняют webhook-настройки и очищают объектный кеш.

```bash
wp eval-file /path/to/plugin_myprintlab/tests/workflow.php
php -l /path/to/plugin_myprintlab/print-proof-workflow.php
node --check /path/to/plugin_myprintlab/assets/ppw.js
```

В подготовленной облачной среде:

```bash
bash /workspace/ppw-dev/start.sh
/workspace/ppw-dev/bin/wp eval-file /workspace/plugin_myprintlab/tests/workflow.php
```

Проверки охватывают четыре кода, действия в интерфейсе, авторизацию и nonce, утверждение, удаление и скидки, оплату, повторную доставку, устаревшие ревизии, реальную HTTP-загрузку замены и multipart callback типографии. Созданные заказы/купон удаляются, webhook-настройки восстанавливаются. Доставка на реальный сервис типографии и отображение в теме рабочего магазина проверяются отдельно с Денисом.
